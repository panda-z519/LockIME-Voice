## What's changed

### Fixed: recording the shortcut no longer triggers your input method

This was the worse half of the 0.1.3 bug. While you recorded the voice shortcut,
the key still reached your input method, which reacted to it and reported
*"shortcut conflict, cannot use global voice"* — so the one thing you had to do
after upgrading could not be done.

Recording now suspends LockIME's claim on the key for as long as the Voice Input
settings pane is open, so the press goes to the recorder instead of to your input
method.

### Changed: back to one shortcut, and it is your input method's voice key

0.1.3 asked for two shortcuts (a LockIME trigger plus the input method's key).
That was the wrong design: it demanded a second recording of a key your input
method already owns, and it let the displayed value drift from the effective one —
which is why the field could show a key you had never set.

There is now a single field. Record the same shortcut you use for voice input
inside your input method; LockIME takes that key over and echoes it back.

**If you are upgrading from 0.1.3:** record your voice shortcut once in
**Settings ▸ Voice Input**. Nothing else is required.

### How the conflict is actually gone

Two things changed together, and both are needed:

| | v0.1.3 | v0.1.4 |
|---|---|---|
| Key handling | listened only (`listenOnly`) | **consumes** the key (`defaultTap`) |
| Who sees the press | your input method **and** LockIME | LockIME only |
| Result | one press handled twice → conflict | handled once |

Consuming the key is what stops your input method from seeing the physical
press, so it has nothing to conflict with. LockIME then sends that same key back
to start recording, marked so its own tap ignores the echo and cannot loop.

**This requires the Accessibility permission**, which 0.1.3 did not ask for.
LockIME needs it to take the key away from your input method. The Voice Input
pane says so and links to the grant; without it the key falls through to the
input method and the conflict returns. The core lock still needs no permissions.

## Install

Ad-hoc signed and **not notarized**. The first launch is blocked by Gatekeeper:

1. Double-click **LockIME Voice**. macOS refuses it with *"Apple could not verify
   that LockIME Voice is free of malware"* — expected, not a broken download.
2. Open **System Settings ▸ Privacy & Security** and scroll to **Security**.
   **LockIME Voice** is listed with an **Open Anyway** button.
3. Click **Open Anyway**, authenticate, then confirm with **Open**.

Then grant **Accessibility** — required for the voice shortcut to work, as
described above. Because the build is ad-hoc signed, reinstalling or rebuilding
can require granting it again.
